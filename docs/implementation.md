Also fixed a real TypeScript 6.0 gotcha: `types` in `compilerOptions` now defaults to empty instead of auto-discovering `@types/*`, so `bun:test`'s ambient types silently disappeared until `"types": ["bun"]` was added explicitly (plus `"allowImportingTsExtensions": true` for Bun-style `.ts`-suffixed imports) — see `docs/architecture.md`. **External review caught two more real issues**: `tsconfig.build.json` needed an explicit `"rootDir": "src"` — TypeScript 6.0 fails declaration emit with TS5011 otherwise, since `outDir` alone isn't enough to disambiguate the output layout (never caught until `build:types` was run in isolation, since the combined `build` script always failed earlier at `build:js` first); and `nextInt(min, max)` now throws a `RangeError` instead of silently returning a nonsensical value when `min > max`.
- [x] **PR 1d — DAG resolver**: `src/core/dag/{types,resolver}.ts`, `src/core/errors.ts` (Kahn's-algorithm topological sort with deterministic ascending-lexical-id tie-break; a `ClinicalFakerError` base class plus `CyclicDependencyError`/`UnresolvedDependencyError`/`DuplicateNodeIdError`/`DependencyNotReadyError` extending it — see `docs/architecture.md`) + 13 tests (linear chain, diamond dependency, tie-break order, unresolved-dependency detection, direct and longer cycle detection, resolving the non-cyclic part of a graph before an unrelated cycle is detected, duplicate node id detection, an undeclared-dependency read hitting the internal ordering guard, error class shape). 100% type coverage, `typecheck`/`lint` clean. The resolver stays generic/domain-agnostic — `DAGNode<TResult>` and `getResult<T>(nodeId)` are type-erased internally (`Map<NodeId, unknown>`), which is what lets future phases plug in new nodes without the resolver knowing about the entity model in advance. That erasure needs exactly one reversal at `getResult`'s single internal `Map.get(...)` read, which is inherently unverifiable by the type checker — documented in place and covered by a `type-coverage:ignore-next-line` (verified live against `type-coverage`'s own docs that `--strict` flags every `as` assertion with no exceptions, and that its ignore-comment mechanism is reported if left unused, so this can't silently go stale). The alternative (a hand-maintained central `NodeResultMap` registry giving fully sound types with zero assertions) was considered and rejected: it would couple the resolver to the whole entity model from this PR onward, contradicting the "plug in nodes without touching the resolver" goal `docs/architecture.md` explicitly designs for. **Self-review before commit caught two real gaps**: two nodes sharing the same `id` were silently allowed (the second one would overwrite the first in the internal lookup, and could then make a perfectly valid graph incorrectly report `CyclicDependencyError` — fixed with `DuplicateNodeIdError`), and one test's name claimed the non-cyclic part of a graph resolves before an unrelated cycle is detected without actually asserting it — fixed to track and check resolution order. **External PR review caught one more (non-blocking)**: `getResult`'s internal guard (a node reading a dependency it didn't declare in its own `dependsOn` before that dependency resolved) threw a plain `Error` instead of a `ClinicalFakerError` subclass — fixed by adding `DependencyNotReadyError`, so a future custom-node author (see the roadmap's Custom Archetype Builder) can catch every error this library throws with one type, including their own node-authoring mistakes.
- [x] **PR 1e — Canonical IR & generator wiring**: `src/entities/types.ts` (full entity set: `PatientGraph`, `Demographics`, `Identifier`, `Address`, `Provider`, `Encounter`, `ConditionEntity`, `ObservationEntity`, `MedicationEntity`, `AllergyEntity`), `src/entities/sampleData.ts` (name/address/gender sampling — the demographic literal data this phase needs, distinct from Phase 4's clinical ontologies), `src/entities/vitalsProjection.ts`, `src/entities/exporters/toJSON.ts`, `src/core/prng/pickFrom.ts`, `src/nodes/{seedNode,demographicsNode,encounterNode}.ts`, `src/generator.ts`, `src/index.ts` + 43 new tests (124 total). 100% type coverage, `typecheck`/`lint` clean, and **`bun run build` passes end-to-end for the first time** (previously expected-failing since `src/index.ts` didn't exist).
  - `createPatient(options?)` returns a `Patient` (`PatientGraph` plus a `.toJSON()` method — since `PatientGraph`'s shape already matches what `.toJSON()` should return per `docs/architecture.md`, `.toJSON()` only adds the computed `vitals` projection on top). Implementing `.toJSON()` as a real method (not just a same-named field) means `JSON.stringify(patient)` invokes it automatically per JS's own serialization protocol, verified with a test.
  - `seedNode` is the DAG's root: it produces the patient's own id (`generateSeededUUID`) and a `referenceDate` deterministically derived from the seed via a fixed anchor date (2024-01-01 UTC) plus a seeded offset — never wall-clock "now". `demographicsNode` and `encounterNode` both depend on it to read `referenceDate` (needed for `dob` derivation and encounter timing respectively). `encounterNode` does **not** depend on `demographicsNode` — an earlier note in `docs/architecture.md` described that dependency, written before `seedNode` existed as a design; encounter's only real current need is `referenceDate`, so the dependency was corrected rather than added as unused speculative wiring.
  - No archetype exists yet (Phase 4), so `demographicsNode` samples age from a fixed realistic adult range (18–90) and gender from a distribution weighted toward male/female (48%/48%) with a small other/unknown tail (2%/2%) rather than a uniform 4-way split, which would look unrealistic for a generic patient population. `conditions`/`observations`/`medications`/`allergies` are empty arrays until Phase 4 archetypes populate them.
  - **A real Bun bundler bug was caught by actually running the built output, not trusting `bun run build`'s exit code**: `package.json`'s `"sideEffects": false` was silently tree-shaking away the *entire* contents of `src/index.ts` (a pure re-export barrel) down to a dangling `export {...}` statement referencing nothing — `bun run build` reported success throughout. Fixed by switching to the array form, `"sideEffects": ["./src/index.ts"]`, which still declares every other module side-effect-free for tree-shaking (including future ontology data modules) while exempting the one file whose entire job is re-exporting. Filed as product feedback; documented in full in `docs/architecture.md`'s "Multi-entry build (verified)" section.

## Later phases (not yet designed in detail)

We go through the library one piece at a time — each phase below gets its own detailed design discussion (types, algorithms, file layout) when we actually start it, not before. Locking in speculative detail for a phase we haven't started tends to get revisited anyway once the prior phase's real constraints are known.

- **HL7 v2 serialization** — segment/composite builders and message assembly (`ADT^A01`/`A08`, `ORM^O01`, `ORU^R01`), compiled from the canonical IR. Testing plan includes cross-validating generated messages against an independent parser, [`hl7v2`](https://github.com/panates/hl7v2) (npm, MIT, devDependency only — never shipped; TypeScript-native and actively maintained, chosen over Redox's `@redox-opensource/redox-hl7-v2` — see `docs/architecture.md`), rather than relying solely on round-trip tests against our own serializer.
- **FHIR R4 compilation** — resource builders and bundle assembly, compiled from the same canonical IR. Testing plan includes cross-validating generated bundles against the official HL7 FHIR reference validator via `fhir-validator-wrapper` (devDependency only; requires a JVM in CI, added via `actions/setup-java` when this phase starts).
- **Clinical archetypes + bundled ontology subsets** — `AdultHypertension`, `Type2Diabetes`, and the ICD-10-CM/RxNorm/LOINC/UCUM data they draw from. `GenerationOptions.archetype` is typed `keyof typeof ARCHETYPES | ArchetypeDefinition` (compile-time protection against a misspelled name); `createPatient()` throws `UnknownArchetypeError` (extends `ClinicalFakerError`) as the runtime fallback — see `docs/architecture.md`'s "Invalid archetype handling". `ArchetypeDefinition` also carries an optional `demographicConstraints` (age range / compatible genders) so a future archetype that only makes sense for one sex or age range can't be paired with contradictory demographics — see "Demographic plausibility". `ObservationDistributionSpec` gains a `clamp: { min, max }` (physically-possible bounds, distinct from the clinical `referenceRange`) since unbounded Gaussian sampling can otherwise produce impossible values; `numericalSamplersNode` resamples toward it (bounded attempts) rather than clamping outright. `abnormalFlag` is always computed from `value` vs `referenceRange`, never independently generated — see "Generation plausibility invariants".
- **Tracked but deferred to Phase 4's design pass**: timestamp ordering so `ObservationEntity.effectiveDateTime` falls within its `Encounter.period` and `ConditionEntity.onsetDate` relates sensibly to the encounter (likely needs `numericalSamplersNode` to declare a DAG dependency on `encounterNode`, not yet declared); MRN uniqueness isn't guaranteed across different seeds (not urgent, no current use case relies on it).
- **Ontology licensing & data-accuracy audit** — verify current LOINC/UCUM/RxNorm/ICD-10-CM redistribution terms from authoritative sources once we know exactly what's bundled, and add `THIRD_PARTY_NOTICES.md`; also verify every bundled code+display pair against free, no-auth NLM/Regenstrief sources (NLM Clinical Table Search Service for ICD-10-CM/LOINC, the RxNorm REST API, `@lhncbc/ucum-lhc` for UCUM — see `docs/architecture.md`'s "Ontology data-accuracy verification").
- **MLLP mock server** — a later, lower-priority phase (not next after archetypes); zero-dependency TCP mock with byte framing and auto-ACK. Design deferred until we get here.
- **CD: automated npm publish** — release workflow, after the above are far enough along to have something worth publishing. **Publish policy**: publish early as `0.x` once something minimally useful exists (e.g. after HL7/FHIR compilation lands), explicitly documented as unstable pre-1.0 — `1.0.0` means all MVP phases (through MLLP) are complete and the public API (`.toJSON()`/`.toHL7()`/`.toFHIR()` shapes) is considered stable. The version-bump/changelog tool (semantic-release vs. changesets) is a separate decision for when this phase actually starts. Also add, closer to release rather than in every-PR CI: a smoke-test step that installs the *built* package with plain `npm`/Node (not Bun) and confirms a basic import/`createPatient()` call works, to actually back up the README's cross-package-manager compatibility claim instead of leaving it unverified. ~~When the repo goes public for release, enable GitHub branch protection~~ — done: the repo went public and branch protection on `main` is now enabled (PR required to merge, enforced for admins too, force-pushes and deletion disabled, 0 required approvals since there's a single maintainer). No required status checks yet — add the CI check as required once PR 1b lands, so it doesn't deadlock merges against a check that's never run.
